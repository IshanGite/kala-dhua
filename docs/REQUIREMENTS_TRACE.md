# Requirements trace: the original problem statement against what is built

Source: "Ragnarok Research Proposal: A Sovereign, Always-On Personal AI Agent" (FR1.1 to FR4.2, NFR1.1 to NFR4.3).
Status words: DONE (implemented, tested, and exercised live), DONE-UNIT (implemented and tested; not yet exercised on real accounts), PARTIAL (works, with a named gap), OPEN.
Evidence files live in `docs/evidence/` (generated by scripts in `scripts/`) and `docs/spikes/`. Test names are in `tests/`.

## Non-functional requirements

| Req | Gate | Result | Evidence |
|---|---|---|---|
| NFR1.1 Local-first | all raw data, memory and logs on the user's hardware; nothing sent to third-party servers | everything is stored locally; the only network traffic is to the services the user connected, for data they asked to read or send; logs hold codes and counts only | `test_NFR1_3_local_inference` (lints), `test_hygiene` |
| NFR1.2 Encrypted at rest | database encrypted with user-held keys | SQLCipher, master key in the OS keychain, per-file keys wrapped, crypto-shred on delete; wrong-key and header tests | `test_NFR1_2_encrypted_store` |
| NFR1.3 Fully local inference | no external LLM API | Ollama on 127.0.0.1 plus Laya in-process; a test fails the build if a cloud AI library or key appears; model allowlist pinned by digest in `models.lock` | `test_NFR1_3_local_inference`, `test_gateway_backends` |
| NFR2.1 Responsiveness | under 800 ms for memory retrieval and intent classification | retrieval p50 45 ms, p95 94 ms, p99 98 ms; classification: questions 0 ms, commands 34 ms, ambiguous wording p50 539 ms, p95 664 ms (one outlier 860 ms) | `docs/evidence/nfr2_1.json` |
| NFR2.2 Resource footprint | agent plus inference at most 30 percent of the machine | CPU share of the whole machine (10 cores), agent plus Ollama's model processes: idle with polling mean 1.45 percent, p95 4.1 percent, max 11.8 percent (a poll that embeds new messages); under 60 s of back-to-back real-model requests mean 4.9 percent, p95 12.2 percent, max 12.2 percent; agent process alone 0.3 percent and under 300 MB of memory. CPU only: the Apple GPU load is not measurable without root, so it is not claimed | `docs/evidence/nfr2_2_idle.json`, `nfr2_2_load.json` |
| NFR3.1 Graceful degradation | one failing tool halts only that sub-task | a failing source never stops the others; with the model server down, reminders, calendar, time and keyword search still work and other requests say so; failed nodes block only their dependents | `test_NFR3_recovery_and_chaos`, `test_NFR3_executor` |
| NFR3.2 State recovery | restore state within 5 s of reboot | kill -9 mid-task, restart: state back in 3.29 s with the interrupted task asking for its approval again | `docs/evidence/nfr3_2_restart.json`, `test_NFR3_executor` (crash matrix) |
| NFR4.1 Explainability | transparent execution log of why a tool was chosen | every reply has a "Why?" panel (which rung chose, what Laya said, parameters, risk tier, result, timing); `/trace` API; decisions stored in the ledger | `test_P6_agent_actions` (why trace) |
| NFR4.2 User control over memory | view, edit, export, permanently delete | Messages and Remembered in the window: search, edit a fact, delete with preview, confirmation token and a verified receipt (verification scan finds nothing), export JSON or Markdown with provenance | `test_NFR4_2_delete_proof`, `test_NFR4_control_api` |
| NFR4.3 Permission granularity | RBAC with just-in-time approval for high-risk skills | risk tiers 0 to 3 computed from permissions; policy engine; every send, post and calendar or Drive write needs a click on a card bound to the exact content; enabling a skill needs a typed step-up phrase and a delay; typed "yes" can never approve; per-identity grants; budgets | `test_NFR4_3_broker`, `test_policy`, `tests/security/` |

## Known gaps (said plainly)
1. Windows sandbox and Windows notification reader are not implemented (Tushar).
2. Laya is calibrated, not fine-tuned; its confident coverage is about 30 percent.
3. Outlook has not been run against a real account; desktop notifications have not been run against real notifications.
4. Slack posting works only after the app has the `chat:write` scope (done on the demo workspace).
5. The LLM planner fallback is slow (20 to 30 s) and unreliable; common multi-step shapes use the code decomposer.
6. A full red-team report (`docs/RED_TEAM.md`) and a one-command acceptance runner are not finished; the live injection test and the security test suite are the current evidence.
